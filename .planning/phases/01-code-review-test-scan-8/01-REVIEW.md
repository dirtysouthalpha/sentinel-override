## Critical Issues

### CR-01: Unsafe array access without bounds guard in test code

**File:** `tests/quick-assist-handler.test.js:296`
**Issue:** Direct access to `mock.calls[0]` after checking length, creating a TOCTOU (time-of-check/time-of-use) race condition.

The code checks `.length` on line 295, then directly accesses `[0]` on line 296. While unlikely in practice, this creates a potential crash if the mock array is modified between the check and access.

```javascript
expect(global.fetch.mock.calls.length).toBeGreaterThan(0);
const fetchCall = global.fetch.mock.calls[0];  // ← Unsafe if array cleared between lines
expect(fetchCall[1].headers).toMatchObject({
  'Content-Type': 'application/json',
});
```

**Fix:** Use optional chaining or array destructuring with defaults:

```javascript
// Option 1: Optional chaining with fallback
const fetchCall = global.fetch.mock.calls[0] || [];
expect(fetchCall[1]?.headers).toMatchObject({
  'Content-Type': 'application/json',
});

// Option 2: Destructure with default (preferred)
const [fetchCall = []] = global.fetch.mock.calls;
expect(fetchCall[1]?.headers).toMatchObject({
  'Content-Type': 'application/json',
});
```

**Risk:** Test flakiness. In this specific case, the risk is low because Jest mocks are synchronous within the test, but the pattern is unsafe and inconsistent with the rest of the codebase (137 other test files use optional chaining `?.` or guards `||` for similar patterns).

**Pattern inconsistency:** Every other instance of `mock.calls[0]` across 137 test files uses safe access patterns:
- `mock.calls[0]?.[0]` (optional chaining)
- `mock.calls[0] || []` (fallback)
- `mock.calls[0] || null` (fallback)

This is the ONLY file in the entire test suite using unsafe direct access.
