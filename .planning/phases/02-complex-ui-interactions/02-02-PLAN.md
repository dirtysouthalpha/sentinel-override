  <name>Task 1: Implement special input utilities and overlay detection/dismissal</name>
  <files>content/special-inputs.js, content/overlay-detector.js</files>
  <action>
Create two new content utility modules for special input types and overlay handling.

**content/special-inputs.js:**

1. `setDatePickerValue(el, dateStr)` -- Set a date picker value.
   - Strategy 1 (native): If `el.type === 'date'`, use the native setter hack (`Object.getOwnPropertyDescriptor(HTMLInputElement.prototype, 'value').set`) to set the value, then dispatch input + change events.
   - Strategy 2 (framework): If el is a container div wrapping an input, find the input child and apply Strategy 1.
   - Strategy 3 (UI fallback): If neither works, try clicking the date picker trigger to open a calendar, then click the target date. This is a best-effort fallback.
   - Accepts dateStr in "YYYY-MM-DD" format (native) or human-readable format (e.g., "April 24, 2026") which it parses before setting.
   - Returns { success: boolean, method: string, error?: string }
   - All events use `{ bubbles: true, composed: true }`

2. `uploadFile(inputEl, fileName, mimeType, content)` -- Upload a file programmatically.
   - Only works on `<input type="file">` elements. Returns false immediately if not a file input.
   - Creates a `File` object from the content string: `new File([content], fileName, { type: mimeType })`
   - Creates a `DataTransfer` object, adds the file, sets it on `inputEl.files`
   - Dispatches `change` event with `{ bubbles: true, composed: true }`
   - Returns true on success
   - NOTE: The content parameter is a string. For binary files, the agent would need to use execute_js to create the File object. This utility handles text-based file uploads (CSV, JSON, XML, etc.)

3. `setRichTextValue(el, text)` -- Set value in a rich text editor.
   - Strategy 1 (execCommand): Focus the element, select all existing content, delete it, then insert text char by char using `document.execCommand('insertText', false, char)`. Dispatch InputEvent after each char. This works with Quill, TinyMCE, CKEditor, and most contenteditable editors.
   - Strategy 2 (direct set): If execCommand is not available or fails, set `el.innerHTML` directly and dispatch input + change events.
   - Strategy 3 (editor API): Check for known editor instances:
     - `el.__quill` (Quill): use `el.__quill.setText(text)`
     - `tinymce.get(el.id)` (TinyMCE): use `editor.setContent(text)`
     - `window.CKEDITOR?.instances[el.id]` (CKEditor): use `editor.setData(text)`
   - Returns { success: boolean, method: string }

4. `isDateInput(el)` -- Detect if element is a date picker. Checks:
   - `el.type === 'date'`, `el.type === 'datetime-local'`, `el.type === 'month'`
   - Has ARIA role="datepicker" or aria-haspopup="dialog"
   - Parent/container has class containing "datepicker", "calendar", "date-picker"
   - Returns boolean

5. `isRichTextEditor(el)` -- Detect if element is a rich text editor. Checks:
   - `el.isContentEditable === true` AND (has child elements like `<b>`, `<i>`, `<a>`, `<br>` OR has rich text editor classes)
   - Known editor containers: `.ql-editor` (Quill), `.tox-edit-area` (TinyMCE), `.ck-editor` (CKEditor), `.ProseMirror` (ProseMirror), `.lexical-editor` (Lexical)
   - Returns boolean

All functions stored on `window.__sentinelUtils.specialInputs`.

**content/overlay-detector.js:**

1. `detectOverlay(doc)` -- Detect if any overlay/modal is blocking the page. Returns the blocking element or null. Checks in order:
   - ARIA: `[aria-modal="true"]` that is visible
   - Role: `[role="dialog"]` or `[role="alertdialog"]` that is visible
   - High z-index: Any `div` or `section` with `position: fixed`, `z-index > 1000`, full-width/height, and `pointer-events !== 'none'`
   - Cookie banners: Elements with classes/IDs matching common cookie consent patterns (`.cookie-banner`, `.consent-popup`, `#onetrust-banner`, `#cookie-notice`)
   - Use `isVisible` from dom-utils.js and `queryDeep` from shadow-dom.js for shadow DOM compatibility

2. `dismissOverlay(doc, overlay)` -- Attempt to dismiss a detected overlay. Returns true if dismissed (overlay removed from DOM or hidden). Ordered dismissal patterns:
   - Close buttons: `[aria-label="Close" i]`, `[aria-label="Dismiss" i]`, `button.close`, `.close-btn`, `.modal-close`, `[data-dismiss="modal"]`
   - Cookie accept: `.cookie-banner .accept`, `.consent-btn`, `#onetrust-accept-btn-handler`
   - Text match: buttons/a elements whose trimmed textContent matches `/^(close|dismiss|accept|ok|got it|agree)$/i`
   - Escape key: dispatch `keydown` with key='Escape', `{ bubbles: true, composed: true }`
   - Wait 300ms after each attempt, check if overlay is still connected to DOM
   - Stop trying after first successful dismissal
   - NEVER remove overlay from DOM directly (Pitfall 7 from research)

3. `isOverlayBlocking(doc, targetEl)` -- Check if a specific target element is obscured by an overlay. Uses `doc.elementFromPoint` with the target's center coordinates to check if the topmost element at that point is the target itself. If not, the target is blocked. Returns the blocking element or null.

All functions stored on `window.__sentinelUtils.overlay`.

<task type="auto">
  <name>Task 2: Implement same-origin frame manager and cross-origin frame router</name>
  <files>content/frame-manager.js, background/frame-router.js</files>
  <action>
Create iframe interaction support split across content script (same-origin) and background (cross-origin).

**content/frame-manager.js** -- Runs in the main page context, handles same-origin iframes:

1. `scanIframes(doc)` -- Enumerate all iframes in the document. For each iframe:
   - Try to access `iframe.contentWindow.document` (same-origin check)
   - If accessible: recursively scan the iframe's document using the existing `scanDocument` utility from dom-utils.js, with prefix `frame:{index}:`
   - If inaccessible (cross-origin): add a placeholder element to the results:
     ```javascript
     { index: N, tag: 'IFRAME', text: 'Cross-origin iframe: {src}', selector: 'frame:{index}:', role: 'cross-origin-iframe', type: 'none', frameUrl: src, frameId: null }
     ```
   - Returns { elements: [...], iframeCount: N, crossOriginCount: M }

2. `findInIframe(doc, selector)` -- Given a selector starting with `frame:`, resolve the iframe and find the element within it. Enhanced from the existing iframe handling in content.js executeCommand:
   - Parse `frame:{index}:{rest}` selector format
   - For same-origin: access iframe document and use findElementBySelector from dom-utils.js
   - For cross-origin: return { crossOrigin: true, frameIndex, frameUrl, remainingSelector } so the caller can delegate to the background script
   - Also handle nested frame prefixes (though single-level is the priority for this phase)

3. `getIframeInfo(doc)` -- Return metadata about all iframes: index, src URL, same-origin status, dimensions, visibility. Used by the LLM to understand what iframes are on the page.

All functions stored on `window.__sentinelUtils.frame`.

**background/frame-router.js** -- New ES module in background/, handles cross-origin iframe access:

1. `enumerateFrames(tabId)` -- Use `chrome.webNavigation.getAllFrames({ tabId })` to get all frames in a tab. Returns array of:
   ```javascript
   { frameId, parentId, url, isIframe: frameId !== 0, isCrossOrigin: boolean }
   ```
   Cross-origin detection: compare URL origins between frame 0 (main page) and each iframe.

2. `executeInFrame(tabId, frameId, command)` -- Execute a DOM command inside a specific iframe. This is a TWO-STEP injection process to give the iframe access to the full content/ utility stack:
   - **Step 1: Inject utility modules** into the target frame using `chrome.scripting.executeScript` with the `files` array and `frameIds` parameter (same pattern as tab-manager.js uses for the main page):
     ```javascript
     await chrome.scripting.executeScript({
       target: { tabId, frameIds: [frameId] },
       files: [
         'content/dom-utils.js',
         'content/shadow-dom.js',
         'content/highlight.js',
         'content/wait-utils.js',
         'content/dropdown-utils.js',
         'content/special-inputs.js',
         'content/overlay-detector.js'
       ]
     });
     ```
     This makes scanDocument, findElementBySelector, isVisible, shadow DOM utils, etc. available inside the cross-origin iframe's isolated world.
   - **Step 2: Inject a small command runner script** that uses the already-loaded utilities:
     ```javascript
     await chrome.scripting.executeScript({
       target: { tabId, frameIds: [frameId] },
       func: (command) => {
         // Utilities are now available via window.__sentinelUtils
         const { dom, shadow, overlay, specialInputs } = window.__sentinelUtils;
         // Execute command using the full utility stack...
       },
       args: [command]
     });
     ```
   - The command runner handles: `click`, `type`, `observe_page`, `read_page`
   - Returns `{ ok: true, data: result }` or `{ ok: false, error: string }`
   - **Why two steps:** A single inline function cannot access the content/ utility modules since they're in separate files. By injecting the files first (Step 1), the command runner in Step 2 can reference `window.__sentinelUtils.*` just like the main content script does.

3. `resolveFrameForSelector(tabId, frameIndex)` -- Given a frame index (from the content script's frame:N: prefix), map it to a Chrome frameId using `enumerateFrames`. The mapping is positional: frame index 0 = first iframe in DOM order = first frame with parentId === 0 in webNavigation results.

Import this module from background/index.js. Export all three functions.

**Integration pattern:**
When the content script encounters a cross-origin iframe selector:
1. content/index.js executeCommand detects cross-origin via findInIframe returning { crossOrigin: true }
2. content/index.js sends a message to background: `{ action: 'execute_in_frame', frameIndex, command }`
3. background/index.js routes to frame-router.executeInFrame
4. Result flows back to content/index.js which returns it to agent-engine

**content/index.js changes:**

   - Before the standard INPUT/TEXTAREA handling, check `isRichTextEditor(el)` from special-inputs.js
   - If rich text editor: call `setRichTextValue(el, cmd.text)`, return result
   - If date input detected via `isDateInput(el)`: call `setDatePickerValue(el, cmd.text)`, return result
   - Keep existing contenteditable and standard input handling as fallbacks

2. **Add `upload_file` command type** in executeCommand:
   - `{ type: 'upload_file', selector: '...', file_name: 'data.csv', mime_type: 'text/csv', content: '...file content...' }`
   - Find the file input element by selector
   - Call `uploadFile(inputEl, cmd.file_name, cmd.mime_type, cmd.content)`
   - Return success/error result

3. **Add reactive overlay dismissal** -- add an overlay check at the top of the executeCommand function, BEFORE the switch statement:
   - For `click`, `type`, `select`, `hover` command types: after finding the target element, call `isOverlayBlocking(doc, targetEl)` from overlay-detector.js
   - If overlay detected: call `dismissOverlay(doc, overlay)`, wait 300ms
   - If overlay still present after dismissal attempt: include overlay info in the error result so the LLM knows
   - If overlay dismissed: proceed with the original command normally
   - This is a conditional check at the top of executeCommand, not a wrapper function or decorator. The existing switch/case structure remains unchanged -- just add the check before it for the relevant command types
   - This implements the CONTEXT.md decision: "reactive not proactive" -- only check when executing an action

4. **Update `observe_page` handler** to use scanIframes from frame-manager.js:
   - Replace the existing inline iframe scanning with `scanIframes(document)`
   - Merge the iframe elements into the main element list
   - Cross-origin iframe placeholders are included so the LLM knows they exist

5. **Add `read_iframe` action** in handleMessage:
   - `{ action: 'read_iframe', frameIndex: 0 }`
   - For same-origin: call read_page logic on the iframe's document
   - For cross-origin: return `{ ok: false, error: 'Cross-origin iframe -- use background routing' }`

6. **Handle cross-origin iframe commands** in executeCommand:
   - When findInIframe returns `{ crossOrigin: true }`, send a dedicated message to the background script:
     ```javascript
     chrome.runtime.sendMessage({ action: 'execute_in_frame', frameIndex, command }, (response) => {
       // Return response to agent-engine
     });
     ```
   - Do NOT throw an error -- errors propagate directly to agent-engine as failures. The background/index.js `execute_in_frame` handler receives this message and routes to `frame-router.executeInFrame`. The response flows back through the callback.

**background/index.js changes:**

2. Add `execute_in_frame` message handler:
